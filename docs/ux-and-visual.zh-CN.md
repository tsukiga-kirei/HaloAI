# HaloAI 用户体验与视觉规格

## 目的

本文定义 HaloAI 的用户体验、响应式信息架构、交互规则、视觉语言、无障碍基线、性能预算与视觉验收门槛。

HaloAI 是一个以人为主导的工作房间。对话帮助人员协调，而文档、决策、任务、审批和审计记录保存长期成果。界面必须让人的责任、AI 的参与、当前工作状态与下一项有效操作清晰可见，同时不能把产品变成监控仪表盘。

## 体验原则

1. **成果先于对话。** 聊天是入口；长期工作应沉淀为文档、决策、任务和审批。
2. **人的责任始终可见。** AI 可以在委托范围内提议和执行，但目标所有权、批准权和最终发布责任必须归属到人。
3. **身份不得模糊。** 人、AI 和系统主体使用一致的消息结构，但必须通过文字标签、头像样式和无障碍名称明确区分。
4. **保持沉默也是能力。** 只有被明确提及的 AI，或由已启用协调员选出的最小必要参与者集合，才应响应。
5. **进度可观察。** 产品应说明 AI 运行处于排队、读取已授权资料、生成、等待批准、完成、停止或失败状态，但不得展示隐藏推理过程。
6. **安全必须容易理解。** 只读工作保持轻量；修改、外部影响和敏感行为必须展示范围、差异、责任主体和审批要求。
7. **移动端是一条专门设计的工作流。** 它不是压缩后的桌面仪表盘。
8. **克制也是质量。** 内容、层级与留白承担主要表达，品牌效果保持节制。

## 信息架构

### 全局层

- 登录、注册与账户恢复
- 工作区切换器
- 全局搜索
- 收件箱：提及、邀请、审批与工作完成通知
- 用户设置：语言、主题、通知偏好、设备与安全

### 工作区层

- 工作区概览
- 房间
- 文档
- 人员与 AI 成员
- 活动记录
- 工作区设置
- 成员、访问角色与邀请
- 仅向授权成员开放的审计记录

### 房间层

每个工作房间包含：

- 目标与状态
- 人类与 AI 参与者
- 对话与线程
- 关联文档和其他长期成果
- Agent 运行状态
- 审批请求
- 随产品演进加入的决策与任务

建议路由模型：

```text
/{locale}
/{locale}/inbox
/{locale}/w/{workspaceSlug}
/{locale}/w/{workspaceSlug}/rooms/{roomId}
/{locale}/w/{workspaceSlug}/docs/{documentId}
/{locale}/w/{workspaceSlug}/actors
/{locale}/w/{workspaceSlug}/settings/members
/{locale}/w/{workspaceSlug}/settings/roles
/{locale}/w/{workspaceSlug}/settings/audit
```

路由标识和 slug 保持稳定，不进行翻译。

## 响应式应用外壳

断点描述的是布局行为，而不是设备身份。界面必须在各检查点之间连续可用，不能只适配几个精确宽度。

| 视口 | 必须采用的布局 |
| --- | --- |
| `>= 1440px` | 64px 工作区栏、256–288px 房间导航、对话区、文档区，以及可选的 320–380px 上下文抽屉 |
| `1200–1439px` | 工作区栏、240–256px 房间导航、一个主要工作面；可选对话/文档分屏；上下文内容进入抽屉 |
| `768–1199px` | 一次显示一个主要工作面；房间导航进入抽屉；使用对话/文档分段切换；上下文详情进入侧边或底部面板 |
| `< 768px` | 单视图导航栈、紧凑顶部栏、一个对话或文档工作面、底部导航，以及适配 safe-area 的输入器或编辑工具栏 |

### 宽屏桌面

在 1440px 及以上，房间主要体验采用房间 / 对话 / 文档三部分结构。最左侧可以存在窄工作区栏，但不得与三个工作区域争夺注意力。

用户可以选择：

- **对话专注：** 对话为主，文档作为次要面板保持可见。
- **文档专注：** 文档为主，与文档相关的讨论保持在旁侧。
- **分屏工作：** 对话约占 40%，文档约占 60%；分隔线可调整并记住用户偏好。

任何工作面板不得缩小到 480px 以下。可用宽度不足时，应先收起上下文内容，而不是压缩阅读区域。

### 平板

- 一次只展示一个主要视图。
- 房间导航放入抽屉。
- 使用分段控件切换对话与文档。
- 只在足够宽的横屏布局中允许临时分屏。
- 参与者、来源、审批和运行详情进入侧边抽屉或底部面板。
- 保持较大的触控目标和可读字号，不能直接缩小桌面外壳。

### 手机

房间使用单视图导航栈：

```text
顶部栏：返回、房间名称、连接状态、更多操作
主体：当前对话或文档
底部：消息输入器或移动编辑工具栏
```

工作区底部导航包含四个稳定入口：

- 对话
- 文档
- 收件箱
- 我的

移动端要求：

- 支持最低 320px 宽度。
- 使用 `100dvh` 和 safe-area inset。
- 软件键盘弹出时保持输入器可见。
- 文档编辑进入全屏专注视图。
- 批注、来源和 AI 提案使用底部面板。
- 每个 hover、右键或拖拽行为都必须有点击替代路径。
- 不得产生非预期水平滚动。

## 核心页面

### 工作区概览

首屏需要回答四个问题：

- 这个工作区准备完成什么？
- 最近哪些房间发生了变化？
- 哪些文档需要审阅？
- 哪些事项需要我的回应或批准？

初始模块为工作区目标、最近房间、待处理审批、最近文档和提及。视觉最强的操作是**新建房间**。空状态必须提供一个明确下一步，不能只依赖插画。

### 房间

房间头部包含：

- 房间名称与简短目标
- 状态：进行中、等待审批、已完成或已归档
- 人类与 AI 参与者头像组
- 关联文档入口
- 对话/文档/详情切换
- 搜索与更多操作

对话规则：

- 空间允许时，将可读消息列保持在 760–880px。
- 人类与 AI 消息使用相同阅读节奏；AI 内容默认不得变成视觉上过大的卡片。
- AI 头像使用细 Halo 光环，并显示明确的 `AI` 标签。
- 系统事件使用紧凑时间线样式。
- 工具活动使用普通语言摘要，默认折叠。
- 来源、模型用量、工具详情和运行历史采用渐进披露。
- 绝不渲染模型隐藏推理。

### 文档

编辑器内容宽度保持在 720–820px，以获得舒适阅读体验。头部包含标题、同步状态、当前协作者、版本历史、分享和权限控件，以及 AI 协作入口。

编辑规则：

- 自动保存，并使用低干扰同步提示。
- 展示远程光标与选区，但不得遮挡正文。
- 批注与正文事实状态分离。
- AI 修改默认作为可审阅提案。
- 支持接受单项、全部接受、拒绝或要求修改。
- AI 修改被接受后创建长期版本检查点。
- 移动端仅在键盘上方保留最重要的格式工具。

### 人员与 AI

目录使用统一的 Actor 展示方式，同时明确标记人类、AI 成员、访客和已停用 AI。

AI 资料卡展示：

- 名称、头像和 AI 身份标签
- 协作角色与一句话职责
- 获准读取的知识范围
- 被允许的能力和工具
- 审批要求
- 运行预算与最大步骤
- 当前可用状态

创建流程包含五步：

1. 身份：名称、头像和介绍。
2. 职责：目标、擅长事项和明确不负责事项。
3. 知识：允许读取的房间与文档。
4. 能力：工具、写入范围和审批门槛。
5. 行为：回复语言、主动程度、预算和运行上限。

供应商、模型和采样参数放在高级设置中，不应成为普通成员的首要心智模型。

### 收件箱

收件箱统一容纳提及、审批请求、邀请和后台工作完成通知。每一项展示所属工作区与房间、主体身份、发生时间和需要完成的操作。用户可以按类别筛选，并在不离开当前上下文时标为已读。

### 权限与错误状态

- 在安全允许披露原因时，禁用操作应解释缺少的能力。
- 直接访问无权资源时，根据策略返回不泄露信息的未找到或禁止状态。
- 错误必须保留用户输入，并提供重试、复制或恢复操作。
- 空、加载、离线、重连、只读和失败状态都是一等界面，不能只是临时追加一行文字。

## 核心用户路径

### 创建工作房间

1. 输入名称与简明成果目标。
2. 邀请人类参与者。
3. 加入最小有用的 AI 参与者集合。
4. 检查每个 AI 的可读范围与能力。
5. 创建房间，并进入带有建议首项操作的空对话。

创建房间时不要求选择高级协作模式；默认使用明确提及模式。

### 发送消息并调用 AI

1. 编写消息，并可引用人、AI、文档和附件。
2. 发送前展示将要运行的 AI 成员。
3. 立即插入乐观人类消息。
4. 使用客户端 mutation 标识与服务端结果对账。
5. 为每个 AI 运行展示清晰状态和停止操作。
6. 发送失败时保留消息，并提供重试和复制。

输入器行为：

- Enter 发送，Shift+Enter 换行。
- 输入法正在组词时，Enter 绝不能发送消息。
- `@` 打开可无障碍操作的参与者选择器。
- 斜杠动作保持少量且经过筛选。
- 跨页面导航和短暂断网时保留草稿。

### 将对话沉淀为文档

1. 选择一条消息或线程。
2. 选择**添加到文档**。
3. 选择现有章节或新建章节。
4. 审阅建议内容与来源归属。
5. 作为人类编辑应用，或提交为 AI 辅助提案。
6. 记录产出主体与来源引用。

### 审阅 AI 提案

1. 打开行内提案卡片或收件箱事项。
2. 比较修改前后内容并检查来源。
3. 接受单项、全部接受、拒绝或要求修改。
4. 应用前检测基准版本是否过期。
5. 将已接受操作作为一次可归属的文档事务应用。
6. 创建版本检查点与审计事件。

### 批准敏感操作

审批界面必须展示发起人、执行 AI、精确目标、参数摘要、预期影响、适用时的差异、外部影响和有效期。操作为**仅批准本次**、**拒绝**和**要求修改**。界面不得提供模糊的“以后总是允许”快捷选项。

## 交互约定

- 一个页面只有一个视觉上最强的主操作。
- 只有在失败可安全对账时才允许乐观界面。
- 破坏性操作使用明确文字，不能只依赖颜色。
- Toast 用于短暂完成反馈；需要决策的错误应留在行内。
- 抽屉保留当前房间上下文；完整页面只用于长期目的地。
- 用户正在阅读历史时，流式内容不得强制滚到底部。
- 使用**有新消息**按钮返回最新内容。
- 重试 AI 回复时创建新版本，不能静默覆盖原回复。
- AI 状态文案描述可观察行为，不得伪装成隐藏推理。

## 国际化与内容

首发语言为 `zh-CN` 和 `en-US`。语言选择优先级：

```text
已保存的用户偏好
> locale cookie
> Accept-Language
> 默认 zh-CN
```

实现要求：

- 使用 locale 路由段和类型化 `next-intl` 消息目录。
- 消息拆分为稳定命名空间，例如 `common`、`navigation`、`workspace`、`room`、`chat`、`document`、`agent`、`permission`、`approval`、`settings` 和 `errors`。
- 语言键或值域不一致时持续集成必须失败。
- 禁止拼接翻译片段形成句子。
- 可变语法使用 ICU plural 和 select。
- 日期、数字、货币和相对时间通过 locale 感知格式器生成。
- API 返回稳定错误码和结构化参数，在界面边界完成翻译。
- 保留用户内容的原始语言，并标记生成式翻译。
- 稳定 Agent 标识与本地化显示名分离。
- 正确设置文档的 `lang` 与 `dir`。
- 使用逻辑 CSS 属性，避免未来 RTL 布局需要结构性重写。
- 持续集成测试文本膨胀伪语言与 RTL 伪语言。

## Quiet Halo 视觉系统

### 品牌表达

Quiet Halo 代表专业、安静、可信和适度的未来感。光环出现于：

- AI 头像周围的 1–2px 细环
- AI 运行时低强度的工作呼吸效果
- AI 工作完成或选中 AI 提案时的轻微径向高光
- 产品标志与少量品牌时刻中更明显的渐变

光环不得出现在长文本背后、每张卡片周围、人类消息上，或成为覆盖整个应用的永久发光效果。

### 语义颜色基础

浅色主题起始值：

```text
canvas          #F7F8FA
surface         #FFFFFF
surface-muted   #F1F3F7
text            #171A21
text-muted      #5E6573
border          #E2E6ED
accent          #6D5CE7
accent-hover    #5B4AD1
halo-start      #7C6CF2
halo-end        #38BDF8
success         #16805A
warning         #A35C00
danger          #C23B3B
```

深色主题起始值：

```text
canvas          #0F1117
surface         #171A22
surface-muted   #20242F
text            #F4F6FA
text-muted      #A9B0BE
border          #2C3240
accent          #9A8CFF
```

这些颜色是初始 token，不代表已经合规。每种文字、图标、边框、焦点和状态组合都必须通过对应对比度检查。

### 字体

使用现代拉丁无衬线字体与系统中文后备字体：

```text
Geist Sans, Inter, ui-sans-serif, system-ui,
PingFang SC, Microsoft YaHei, sans-serif
```

字体层级：

| 用途 | 字号 / 行高 | 字重 |
| --- | --- | --- |
| 页面标题 | `28 / 36` | 600 |
| 二级标题 | `22 / 30` | 600 |
| 区块标题 | `16 / 24` | 600 |
| 正文 | `15 / 24` | 400 |
| 辅助文字 | `13 / 18` | 400–500 |
| 代码与技术数值 | `13 / 20` | 等宽字体 |

普通界面文字不得小于 12px。一个页面最多使用四种字重。关键信息可以换行，不能只有打开 tooltip 后才可理解。

### 间距、圆角、层级与图标

间距序列：

```text
4, 8, 12, 16, 24, 32, 48, 64
```

圆角序列：

```text
控件       8px
卡片      12px
大型面板  16px
胶囊      仅用于状态和短筛选标签
```

仅使用两级阴影：菜单/浮层，以及模态框/抽屉。内容卡片通常使用背景与边框，不使用厚重阴影。

统一使用一套图标，常用尺寸为 16px、20px 和 24px。Emoji 不能代替产品图标。每个纯图标控件都必须有 tooltip 与无障碍名称。

### 动效

```text
即时反馈      120ms
标准过渡      180ms
抽屉或对话框  240ms
```

普通界面动画不得超过 300ms。流式文字不得逐字弹跳。减少动态模式取消位移和呼吸效果，但必须保留状态含义。

## 量化视觉验收

“美观”不等于“使用了渐变、圆角卡片和阴影”。HaloAI 页面必须同时通过客观门槛和人工评分，才算视觉验收合格。

### 客观门槛

以下条件必须全部满足：

- 功能样式只使用语义 token；任意颜色、间距、字号和圆角不得散落在页面代码中。
- 同一视觉列的元素在基准截图中对齐，不得出现肉眼可见的 1–2px 偏移。
- 每个视图只有一个最强主操作。
- 不存在非预期水平滚动、重叠、裁切、断裂边框和被遮挡控件。
- 320、390、768、1024、1440 和 1920px 宽度均经过有意布局。
- 中文、英文、伪本地化、长邮箱和长 AI 名称不会破坏外壳。
- 加载、空、错误、离线、重连、只读和无权限状态完整。
- Skeleton 尺寸接近最终内容，不产生明显布局跳动。
- 文本行长、内容宽度和行高符合本文阅读规则。
- 图标一致，并至少通过两种线索区分人类与 AI。
- Halo 装饰不得压过主要内容和操作状态。
- 浅色、深色、减少动态和 200% 缩放模式保持可用。
- 自动无障碍扫描不得存在 serious 或 critical 问题。

### 人工视觉评分

每个维度按 0–2 分评分：

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 层级 | 不知道从哪里开始 | 基本可理解 | 三秒内识别页面、状态与主操作 |
| 对齐 | 明显不一致 | 少量不一致 | 网格、边缘与基线均有明确意图 |
| 间距 | 拥挤或松散 | 基本可用 | 分组清晰且节奏稳定 |
| 字体 | 混乱且难读 | 可以阅读 | 标题、正文和辅助文字层级自然 |
| 色彩 | 强调色互相争抢 | 基本协调 | 中性色主导且强调色语义明确 |
| 品牌 | 通用模板感 | 有少量特色 | Halo 特征清楚但保持克制 |
| 状态完善度 | 只有正常态 | 覆盖部分状态 | 加载、失败、离线、流式与审批同样精致 |
| 响应式 | 把桌面压缩变小 | 可以使用 | 针对不同形态重新组织信息 |

核心页面总分必须至少达到 14/16，且任何维度不得为 0。只有首次人工评审通过后，才可创建视觉回归基准。截图一致只能防止退化，不能证明第一次设计已经优秀。

## 无障碍基线

HaloAI 以 WCAG 2.2 AA 为目标。

### 键盘与焦点

- 提供跳到主要工作区域的链接。
- 菜单、抽屉、提及选择器、审批操作和编辑器控件均可使用键盘操作。
- 对话框内锁定焦点，关闭后恢复到触发元素。
- 重要路由切换后将焦点移动到主标题或工作区域。
- 明暗主题中焦点环都清晰可见。
- 不得把拖拽作为完成操作的唯一路径。
- 消息输入器必须尊重输入法组词状态。

### 屏幕阅读器

- 使用语义化 header、navigation、main、aside、list 和 article 区域。
- 为图标控件提供明确名称。
- 头像和消息必须朗读主体姓名与人类/AI 身份。
- 宣布 AI 开始、完成、失败和等待审批状态，但不逐 token 朗读。
- 用户阅读历史时，宣布新消息数量但不抢夺焦点。
- 连接和同步状态必须使用文字表达，不能只靠颜色。

### 视觉与触控可达性

- 普通文字达到 4.5:1 对比度。
- 控件、边界、焦点指示和大文字满足各自适用的对比度要求。
- 交互目标不小于 44×44 CSS 像素。
- 所有主要路径在 200% 缩放下仍可完成。
- 尊重 `prefers-reduced-motion`。
- 避免闪烁和无休止装饰动画。

## 性能预算

生产环境第 75 百分位目标：

```text
LCP   <= 2.5s
INP   <= 200ms
CLS   <= 0.05
TTFB  <= 800ms
```

交互目标：

- 导航在 100ms 内响应输入。
- 乐观消息在 100ms 内出现。
- 收到流式数据块后在 100ms 内渲染。
- 编辑器本地输入在 50ms 内响应。
- 同区域协作更新通常在 250ms 内出现。
- 主线程长任务保持在 50ms 以下。
- 正常重连在五秒内重新收敛。

建议压缩 JavaScript 预算：

```text
登录与入口             <= 170KB
工作区与房间外壳       <= 220KB
对话路由               <= 250KB
编辑器增量 chunk       <= 280KB
首屏字体载荷           <= 120KB
普通首屏图片           <= 200KB
```

编辑器与协作运行时按需加载。房间首次只加载最近 30–50 条消息。长房间使用窗口化，即使历史包含数千条消息，也只保持约 100–150 个活跃消息节点。流式更新批量处理，头像和预览延迟加载，文档投影不得进入交互渲染关键路径。

## 视觉与交互验证

必须覆盖的视口矩阵：

```text
桌面 Chromium   1440x900   zh-CN   浅色
桌面 WebKit     1440x900   en-US   深色
平板             768x1024   zh-CN
手机             390x844    zh-CN 与 en-US
小屏手机         320x568    文本膨胀
```

每个核心页面必须为有内容、空、加载、错误、离线、无权限、AI 流式输出和审批状态提供确定性截图。测试固定时间、数据和模型输出；等待字体与稳定 ready 标记；禁用动画和 caret；只遮罩真正不确定的光标或时间。

持续集成使用一致的浏览器镜像，默认最大差异像素比例为 `0.002`。任何可见结构变化仍需人工检查。自动检查还必须断言不存在非预期水平溢出、焦点可见、输入器和主控件未被遮挡、无障碍名称齐全、触控目标达到 44px，并且不存在 serious 或 critical 无障碍问题。

## 完成定义

一项用户功能只有满足以下条件才算完成：

- 桌面、平板与手机均有有意设计的布局。
- `zh-CN` 与 `en-US` 语义完整。
- 加载、空、错误、离线和禁止访问状态存在。
- 键盘、触摸与屏幕阅读器用户都能完成主路径。
- 乐观变化可以安全对账或回滚。
- AI 身份、运行状态、停止、重试和责任归属可见。
- 文档修改保持可审阅、可归属。
- 性能预算与无障碍门槛通过。
- 视觉评分达到至少 14/16，且没有 0 分项。
