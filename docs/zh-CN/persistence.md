# HaloAI 持久化与租户事务规范

## 目标

PostgreSQL 是工作空间、成员、房间、消息、文档、Agent 运行、审批、审计与 Outbox 的事实权威。本规范定义内部 Alpha 的连接角色、迁移、租户上下文与首批 repository 行为。

## 连接角色

| 角色     | 用途                       | 允许                              | 禁止                                        |
| -------- | -------------------------- | --------------------------------- | ------------------------------------------- |
| 迁移连接 | 受控发布时执行 schema 迁移 | DDL、迁移记录、为应用角色授予权限 | 进入请求、Worker 或模型调用路径             |
| 应用连接 | API、Worker 与协作持久化   | 经 RLS 过滤后的业务读写           | 拥有表、`BYPASSRLS`、建库、建角色和任意 DDL |
| 认证连接 | 后续认证组件专用           | 用户、会话与账号关联              | 读取业务内容或代表 AI 建立人类会话          |

开发环境的数据库口令放在 `.env.local`（或生产密钥环境）中，由 compose 注入容器，再由 `deploy/postgres/init` 在空库第一次启动时创建登录角色。生产使用同一组变量名，但必须换成独立高强度口令；不要提交真实密钥。已有数据卷不会重新执行 init。

## 租户事务

1. API 先从可信会话解析 `workspaceId` 与 `actorId`，禁止直接信任请求体或 URL 中的租户标识。
2. 每次业务操作必须进入数据库事务。
3. 事务使用 `SET LOCAL` 写入 `haloai.workspace_id`、`haloai.actor_id` 与 `haloai.request_id`。
4. RLS 在缺少或不匹配工作空间上下文时自然返回空集或拒绝写入，禁止回退为全库查询。
5. Repository 只能接收已设置上下文的事务，不得直接持有全局连接池。
6. 事务结束后 `SET LOCAL` 自动清除，池化连接不得携带上一个请求的上下文。

RLS 只是纵深防御。项目成员、房间成员、资源动作与 AI 能力仍由服务端应用策略复检。

## 迁移规则

- `packages/db/src/schema` 是类型化 schema 真源，`packages/db/drizzle` 保存可审查 SQL。
- Schema 版本使用 Drizzle Kit 追加编号迁移（`0000_foundation.sql` 起），由 `pnpm db:migrate` 应用到 PostgreSQL，并记录在 `drizzle.__drizzle_migrations`。这不是 Flyway/Liquibase，也不是运行时切换数据库实例。
- 本地虚拟数据使用另一套版本表 `haloai_devdata_revisions`，与结构迁移分离。
- 迁移只向前追加；已进入共享环境的迁移不得改写。
- 使用 expand、backfill、verify、contract 顺序处理不兼容变化。
- 应用启动不得自动执行迁移；部署与迁移使用不同连接和生命周期。
- 每次迁移后重新授予应用角色必要表权限，但应用角色不得成为表所有者。
- 迁移必须在空数据库和已有数据副本上验证，并提供失败恢复说明。

## 首批 Repository 契约

### 项目与房间

- 创建者必须是 active 工作空间成员。
- 创建房间前必须是 active 项目成员。
- 项目和房间创建与创建者成员关系必须位于同一事务。
- `workspaceId` 与创建者 Actor 只来自服务端事务上下文。

### 消息

- 作者必须是 active 房间成员。
- 消息是仅追加事实，编辑和删除不得覆盖原始行。
- 每个房间通过行锁串行分配递增 `sequence`。
- `clientMutationId` 在工作空间、房间与作者范围内幂等。
- 幂等检查与序号分配必须位于同一房间锁内，避免并发重试重复写入。
- 内容摘要由服务端对规范化 JSON 计算，不接受客户端摘要。
- 单条消息最多 50 个结构化内容块和 64 KiB 规范化 JSON。
- 历史消息使用序号游标分页，单页最多 100 条。

## 验收条件

1. 空数据库能够通过受控命令完成迁移。
2. 应用连接没有 `BYPASSRLS`，缺少工作空间上下文时无法读取租户表。
3. 工作空间 A 的事务无法读取或写入工作空间 B 的房间与消息。
4. 两个并发请求使用同一 `clientMutationId` 时只产生一条消息。
5. 连接回池后，下一个事务看不到上一个事务的工作空间设置。
6. 刷新或重启 API 后，已提交消息仍可从 PostgreSQL 恢复。
7. 日志与 API 错误不得包含数据库 URL、密码、原始 SQL 或跨租户资源标题。

## 当前边界

本阶段完成数据库客户端、迁移、租户事务、项目/房间/消息 repository，以及协作快照与发消息 HTTP API。本地虚拟数据与表结构分离：`packages/db/drizzle` 只保存结构迁移，`packages/db/devdata` 只在 `DEMO_MODE=true` 时由 `pnpm db:seed` 写入。前端不再内置假房间、假消息或后台示例数字；登录必须走认证组件校验哈希后的密码。
