# HaloAI 国际化规范

## 1. 目的与规范用语

本规范定义 HaloAI 如何选择用户界面语言、组合消息、表示内容语言、格式化时间与数据、为从右到左布局做好准备，以及如何在持续集成中证明翻译质量。

本文中的“必须”“禁止”“应该”“不应该”和“可以”具有规范意义。国际化是应用边界，而不是最后阶段的文案润色。任何功能只要其可见文本、错误、通知、日期或生成内容绕过这条边界，就不能视为完成。

首发 UI locale 为 zh-CN 与 en-US。架构必须允许在不修改领域 Schema、授权规则、API 错误契约或页面结构的情况下增加其他语言。

## 2. Locale 与语言模型

HaloAI 区分以下四个值，禁止把它们合并成一个：

| 值        | 含义                                 | 作用域         | 示例          |
| --------- | ------------------------------------ | -------------- | ------------- |
| UI locale | 产品界面的语言与格式惯例             | 请求和用户偏好 | zh-CN         |
| 内容语言  | 消息、文档、评论或来源的语言         | 单条内容记录   | fr            |
| 回复语言  | AI 结果所要求的语言                  | Run 或任务     | en-US         |
| 时区      | 展示或调度时间点所使用的民用时间规则 | 用户或工作空间 | Asia/Shanghai |

UI locale 使用来自封闭、类型化白名单的规范 BCP 47 标签。内容语言标签可以表示尚未作为 UI locale 支持的语言。内容语言未知时保存为 und，禁止在可信度不足时强行猜测。

Locale 绝不能授予访问权、改变 Actor 身份、选择租户或改变策略。经过本地化的路由和消息参数在验证前都是不可信输入。

## 3. Locale 协商、路由与持久化

### 3.1 解析顺序

Locale 协商由服务端负责。已认证请求按以下顺序解析有效 UI locale：

1. 有效的用户已保存偏好；
2. 有效的 locale Cookie；
3. Accept-Language 中与支持列表最匹配的语言；
4. zh-CN。

未认证请求跳过用户偏好步骤。不支持、格式错误、只有通配符或长度异常的语言 Header 必须被安全忽略。匹配不区分大小写，规范化标签大小写，遵守质量权重；只有存在明确映射时，才可把特定标签降级为受支持的父标签。禁止使用子字符串匹配。

Locale 路由段是解析结果的规范表达，不是第二个隐藏偏好。当路由段缺失、不受支持或与更高优先级的已保存偏好冲突时，服务端只重定向一次到等价的规范本地化路由。API、静态资源、回调、健康检查和实时端点不放在 locale 路由之下。

### 3.2 选择与切换

显式切换语言的操作必须：

1. 根据支持列表验证目标 locale；
2. 在用户已认证时保存账户偏好；
3. 更新具有签名或完整性保护的 locale Cookie；
4. 保留当前工作空间和资源路由；
5. 只替换 locale 路由段；
6. 刷新服务端渲染内容，但不丢失编辑器中的未保存状态；以及
7. 以无障碍方式播报语言变化。

切换语言禁止重复执行 mutation、重启 AI Run、重复提交表单或清除草稿。偏好写入失败时，可以在当前会话继续使用本地选择，但界面必须说明该选择尚未保存。

### 3.3 Cookie 与缓存规则

Locale Cookie 只包含受支持的 locale 标识。它不携带授权数据，也绝不作为身份凭据。SameSite、Secure、Path 与存续期设置遵循会话威胁模型。

本地化 HTML 响应必须把 locale 纳入缓存键；协商依赖请求 Header 时设置适当的 Vary 策略。私有工作空间页面禁止进入公共共享缓存。重定向只保留白名单内的站内路径，防止开放重定向。

## 4. TypeScript locale 契约

支持的 locale 集合和默认值在国际化 Package 中定义一次，由 Web 应用、API 展示层、Worker、通知渲染器和测试共同导入。

```ts
export const supportedLocales = ["zh-CN", "en-US"] as const;
export type Locale = (typeof supportedLocales)[number];
export const defaultLocale: Locale = "zh-CN";

export interface LocaleContext {
  locale: Locale;
  timeZone: string;
  source: "account" | "cookie" | "header" | "default";
}
```

代码只有在验证后才能使用 Locale 类型。未经验证的字符串仍然是 string。禁止把请求数据直接断言成 Locale。

Locale 解析器是使用表驱动测试覆盖的纯函数。框架 Adapter 可以读取 Cookie 与 Header，但解析器只接收规范化输入，并返回 locale 及其来源。由此保证浏览器、服务端、Worker 与测试行为一致。

## 5. 消息目录架构

### 5.1 Namespace 与归属

消息目录按稳定产品领域拆分：

- common；
- navigation；
- account；
- workspace；
- room；
- chat；
- document；
- agent；
- tool；
- permission；
- approval；
- notification；
- settings；
- validation；以及
- errors。

每个 Key 只有一个归属领域和一条简明使用说明。只有含义、大小写、参数与无障碍语境确实完全相同时，文案才能进入 common。

### 5.2 类型化 Key 与参数

消息 Key 是 approval.request.expires、error.permission.denied 这类稳定标识。英文句子、路由路径、数据库 ID 和拼接字符串都不能作为 Key。

规范目录 Schema 生成或推导：

- MessageKey：所有有效 Key 的联合类型；
- MessageArgs<K>：Key K 所需与可选 ICU 参数；
- RichMessageKey：允许使用已批准富文本标签的 Key 子集；以及
- Namespace：有效的懒加载边界。

翻译接口具有以下语义契约：

```ts
function translate<K extends MessageKey>(
  key: K,
  values: MessageArgs<K>,
  context: LocaleContext,
): string;
```

禁止动态构造 Key、任意字符串索引以及 translate(valueFromApi) 这类回退。当有限状态映射到文案时，代码使用从状态到 MessageKey 的穷尽类型化 Record。

每个 locale 必须具有与规范目录完全一致的 Key 集合和兼容的参数域。缺失 Key、孤立 Key、占位参数类型变化或 plural 分支缺少 other 都会导致构建失败。

### 5.3 Key 生命周期

Key 描述语义，而不是当前措辞。仅修改文案时保留原 Key。当新旧语义需要并存，或缓存任务需要确定性渲染时，语义变化必须使用新 Key。

删除 Key 前必须证明应用调用、已入队通知、持久化模板、测试和迁移路径均不再引用它。弃用 Key 必须有负责人和移除版本，禁止永久别名。

## 6. ICU 消息组合

消息使用 ICU Message 语法处理 plural、select、selectordinal、number、date 与 time。完整句子必须位于消息目录中。

强制规则：

- 禁止把翻译片段拼接成句子。
- 禁止假设英语语序或单复数语法。
- 当语法存在差异时，使用 select 表达人类、AI、服务、未知和 other 身份措辞。
- plural 必须包含 other；zero、one、two、few、many 只在对应 locale 确实需要时出现。
- 标点属于被翻译消息的一部分。
- 使用 actorName、itemCount 这类语义参数，禁止位置参数。
- 当消息格式器应负责格式时，禁止嵌入预格式化日期、数字或货币。
- Translator Description 必须说明有歧义的名词、动作方向、UI 长度约束，以及某个值是否由用户创作。

目录在构建阶段解析并编译。由用户、模型、连接器或 API 提供的 ICU 语法永远只是数据，绝不能成为可执行消息语法。

## 7. 参数值、富文本与转义

所有变量值默认不可信。纯文本消息根据输出上下文转义 Markup。富文本消息使用封闭标签白名单，标签渲染器是应用自有组件；目录禁止提供任意 HTML、事件处理器、样式、URL 或组件名。

本地化消息中的链接使用类型化站内目的地或应用自有的外部常量。翻译人员不能引入新目的地。用户名、工作空间名、AI 展示名、文件名和引用内容必须与周围双向文本隔离。

即使某个 locale Key 请求这些内容，消息也禁止包含密钥、Access Token、原始授权细节、隐藏策略规则、Stack Trace 或租户标识。国际化绝不能削弱日志脱敏或隐私策略。

## 8. API 错误与校验

领域层与 API 层返回稳定、机器可读的错误，而不是本地化展示句子：

```ts
interface ApiError {
  code: ErrorCode;
  params?: Record<string, string | number | boolean>;
  field?: string;
  retryAfterMs?: number;
  traceId: string;
}
```

ErrorCode 是版本化联合类型。每个 Code 必须穷尽映射到一个 UI MessageKey 和安全参数 Adapter。客户端在展示边界使用当前 locale 完成本地化。

规则：

- HTTP Status 与 Error Code 语义不受 locale 影响。
- Params 只包含安全的结构化值，禁止包含已经拼好的句子片段。
- 字段校验使用稳定字段标识与原因 Code。
- 未知 Code 展示本地化通用错误，并保留 traceId 供支持排查。
- 重试、遥测与自动化只能依据 Code 分支，禁止依据翻译文本。
- 服务端日志记录 Code 与安全诊断，不记录每一种渲染语言。
- 认证与授权错误禁止通过不同措辞泄露额外的资源存在信息。

通知与 Worker 失败使用同一错误 Code 注册表。修改展示文案绝不能改变重试或策略行为。

## 9. 数字、货币、单位、列表与名称

所有格式化都通过共享类型化 Helper 使用 locale 感知的 Intl Formatter。组件禁止临时字符串替换或手工追加单位标签。

- 数字根据业务语义明确精度、舍入模式与记数法。
- 百分比必须一致存储为比率或百分数，并记录该选择。
- 金额携带 ISO 货币 Code 与最小货币单位语义；禁止由 locale 猜测币种。
- 度量值携带类型化单位和明确换算策略。
- 列表使用 locale 感知的合取或析取格式。
- 支持时，人类可读的展示名使用 locale Display Name 格式化。
- 机器标识、Handle、URL、代码、文件路径、模型 ID 与审计 ID 永不翻译。

展示用格式化值禁止再用于持久化、计算、排序、签名、幂等键或 API Payload。

## 10. 时区、日期与调度

持久化时间戳以足够精度表示 UTC 时间点。Locale 与时区是两个独立输入。

展示时区按以下顺序解析：

1. 有效的用户已保存时区；
2. 有效的工作空间默认时区；
3. 经过验证的浏览器 IANA 时区；
4. UTC。

只接受运行时数据集中存在的 IANA 时区标识。固定数字 Offset 不保存为长期时区偏好，因为它不包含夏令时变化规则。

要求：

- API 使用带 Z 或明确 Offset 的 ISO 8601 时间点。
- UI 格式必须明确日期是绝对时间、相对时间、纯日期、纯时间还是日期时间。
- 相对时间必须具有无障碍可获取的绝对时间等价表示。
- 夏令时切换期间存在歧义或不存在的本地时间必须显式消歧。
- 调度工作保存预期本地日期时间、IANA 时区、重复规则与解析后的下一时间点。
- 纯日期业务值禁止通过 UTC 午夜转换。
- 一周起始日和日历标签遵循 locale 策略，禁止手写数组。
- 测试固定时间点与时区，禁止依赖 CI 机器时钟。

审计与安全界面展示无歧义的绝对时间戳和查看者所选时区。导出必须声明采用的时区约定。

## 11. 用户内容、翻译与 AI 语言

### 11.1 原始内容

用户创作的消息、文档、评论、名称与上传文本在接受安全规范化的前提下原样保留。每条实质性内容记录都保存有效语言标签或 und 作为 contentLanguage。禁止把 UI locale 当作内容语言的静默证明。

语言检测可以结合置信度 Metadata 建议标签，但绝不能改写原文；未获得确认时，也绝不能覆盖作者明确选择。

### 11.2 翻译派生版本

翻译是可追踪的派生版本，包含：

- 来源资源 ID 与不可变来源版本或内容 Hash；
- 来源语言与目标语言；
- 翻译状态；
- 创建者 Actor 或服务；
- 适用时的模型或翻译引擎版本；
- 创建时间；以及
- 来源变化后的过期标记。

翻译继承来源资源的租户、权限、分类、保留期、法务保留与删除规则。翻译禁止扩大可见范围、在授权前进入检索结果，或静默替换原文。用户必须能区分原文、生成式翻译、人工编辑翻译和过期翻译。

### 11.3 AI 回复语言

UI locale、会话语言、来源语言和请求输出语言是相互独立的 Run 输入。Agent 优先遵循任务明确指定的语言，其次遵循房间或文档语言策略，最后使用发起用户偏好。解析后的回复语言随 Run 持久化。

系统与策略指令在不同 locale 间保持语义稳定。翻译后的 Prompt 不能授予工具、改变审批规则或修改授权。评测必须验证所有支持 UI locale 和代表性内容语言具有等价安全结果。

### 11.4 搜索与检索

搜索记录内容语言与 Analyzer 版本。查询语言检测可以选择 Analyzer 或多语言检索，但授权过滤必须先于候选内容对调用者的暴露或排序。

搜索结果必须标记译文与原文。存在授权译文时，可使用请求展示语言生成摘要；缺少译文时显示带有明确语言标记的原文，禁止伪造本地化版本。

## 12. 通知、邮件、推送、导出与后台工作

规范通知保存类型化事件 Code、MessageKey、类型化参数、资源目标、收件人作用域与创建时间点。站内通知使用查看者当前 locale 渲染。

外部投递任务在入队时捕获收件人 locale、时区、目录版本与安全模板参数，从而保证重试结果确定。偏好变化只影响新投递，不改变已发送消息的含义。

其他规则：

- Subject、Preview、纯文本与 HTML 来自同一个语义模板。
- Push 与锁屏文本使用隐私安全版本。
- Deep Link 包含规范资源标识，打开时重新授权。
- 退订、同意、安全与法律文本必须具有完整 locale 版本。
- 导出任务在 Manifest 中记录请求 locale 与时区。
- CSV 在需要时保留机器可读原始值，并说明所有本地化展示列。
- 后台任务禁止回退到 Worker 主机 locale。

## 13. RTL 预留、双向文本安全与输入

首发不要求提供从右到左语言，但产品结构必须预先支持。

- 根据验证后的 locale Metadata 设置 html lang 与 dir。
- 使用 CSS 逻辑属性和逻辑 start/end 术语。
- 只有方向图标表达空间含义时才镜像。
- 禁止镜像通用媒体控件、品牌标识、勾选标志或与文本方向无关的符号。
- 适当时为独立用户内容块使用 dir=auto。
- 使用双向隔离包裹插入的名称、ID、Code 与混合方向值。
- 对 Handle、审计标识与安全敏感比较中的危险不可见控制符执行拒绝或可见转义。
- 方向变化后仍要保持键盘顺序、焦点顺序、表格语义和编辑器光标行为。

中文及其他输入法要求输入控件正确处理 Composition。IME 组合期间按 Enter 禁止提交。字符计数、截断、选择、Mention 与搜索按 Unicode 感知边界工作，禁止直接按 UTF-16 Code Unit 处理。

## 14. 伪本地化与布局验证

从规范目录生成两个仅用于测试的 locale：

| 伪 locale | 行为                                                    | 可发现问题                             |
| --------- | ------------------------------------------------------- | -------------------------------------- |
| en-XA     | 为文本添加重音并把普通文案扩展约 35–50%，同时保留占位符 | 裁切、固定宽度、字符串拼接、未翻译文本 |
| ar-XB     | 应用从右到左方向、镜像代表性文本并隔离变量              | 物理 CSS、方向错误、混合文字失败       |

生成过程保留 ICU 结构、富文本标签、键盘快捷键、产品名、代码 Token 与测试 Selector。伪 locale 永远不能成为持久化生产偏好，也绝不能发送给真实用户。

核心页面测试长姓名、长邮箱、大数字、所有 plural 分支、空值、CJK 文本、Emoji、组合字符与混合方向内容。截断绝不能隐藏唯一操作标签、风险警告、权限原因或审批作用域。

## 15. 验证与持续集成门禁

### 15.1 静态目录门禁

每个 Pull Request 都运行：

1. 对 locale、Key 与参数联合类型执行 TypeScript 类型检查。
2. 对 zh-CN 与 en-US 执行完全 Key 对齐检查。
3. 对每个分支执行 ICU 解析与编译检查。
4. 检查占位参数名称与值域兼容性。
5. 检测孤立 Key 与非白名单动态查找。
6. 检测限定生产组件中的禁用原始 UI 字符串。
7. 检查富文本标签白名单与不安全目的地。
8. 确定性生成伪 locale，并断言工作树保持干净。
9. 穷尽检查 API ErrorCode 到 MessageKey 的映射。
10. 检查目录体积与 Namespace 边界。

只有产品名、协议术语、Code 和全语言相同符号等显式白名单内容，完全相同的翻译才只产生 Warning。其他 Warning 都必须由文案审阅者处理。

### 15.2 行为矩阵

强制自动化覆盖包括：

- 已保存偏好、Cookie、带权 Header、非法标签与默认值的协商；
- 不产生循环的规范路由重定向；
- 草稿、Stream、编辑器 Transaction 与 Modal 活跃时的语言切换；
- plural、select、number、currency、date、relative-time 与富文本消息分支；
- 至少两个时区中的夏令时缺口与重叠；
- 通知渲染与确定性重试；
- API 未知 Code 回退与字段错误映射；
- 来源语言保留与过期翻译行为；
- 翻译对租户和权限的继承；
- 不改变权限的 AI 回复语言优先级；
- 键盘与 IME Composition；
- en-XA 与 ar-XB 在桌面和小屏移动宽度的截图；以及
- 不出现水平溢出、不可访问裁切或缺失无障碍名称。

### 15.3 发布门禁

以下任一情况都会阻止发布：

- 任一首发 locale 缺少可达 Key；
- 目录 Schema 或 ICU 参数发生分歧；
- API 可能返回未映射的 Error Code；
- 安全、同意、计费、审批、删除或恢复文案缺少已审阅翻译；
- 伪本地化核心流程溢出或无法操作；
- locale 改变授权、状态机、重试或核算行为；或者
- 新 locale 缺少负责人、回退方案、日期/数字审阅、无障碍审阅和生产回滚方案。

## 16. 运行与完成定义

目录变更与应用代码一起版本化。外部投递记录保留解释实际发送内容所需的目录版本。缺失 Key 与未知错误指标可以包含 locale 和 Key/Code，但禁止包含用户内容。告警用于发现回退率突然升高，禁止把翻译字符串作为指标 Label。

增加生产 locale 必须：

1. 注册规范 locale Metadata 与回退规则；
2. 完成全部必需目录 Namespace；
3. 审阅 ICU 语法、术语、日期、数字与法律文本；
4. 验证字体、换行、输入、搜索与文档导出；
5. 通过伪本地化、视觉、无障碍与性能门禁；
6. 验证通知和支持流程；以及
7. 明确负责人和回滚路径。

一个面向用户的功能只有在两个首发 locale 语义完整、所有可见与辅助文本使用类型化 Key、API 错误保持 locale 无关、内容语言得到保留、日期与数字行为明确、通知渲染确定、RTL 结构安全，并通过本规范全部 CI 门禁后，才算完成国际化。
