# HaloAI 产品需求规格

> 状态：Draft 0.1  
> 适用阶段：Foundation → Internal Alpha  
> 本文定义首个可用产品的范围、行为和验收标准，不定义具体页面实现。

## 1. 产品目标

HaloAI 让一个真实团队在同一项目房间中与多个具名 AI 成员共同完成一份正式成果。产品必须同时解决四个问题：

1. 上下文不再由某个人在聊天、AI 对话和文档之间手工搬运。
2. 每位人员和 AI 的身份、职责和权限清楚可见。
3. AI 的研究、判断和修改可以追踪来源并由人审阅。
4. 讨论能够沉淀为文档、决定、任务和审批，而不是消失在消息流里。

## 2. 非目标

首个版本明确不做：

- 全功能 OA、CRM、项目管理或视频会议平台。
- 必须先画流程图才能使用的低代码工作流产品。
- 默认让所有 AI 自动发言或互相无限调用。
- 允许 AI 静默覆盖共享文档或执行不可逆外部操作。
- 通用 Shell、任意 SQL、任意网页访问和自动安装插件。
- 原生 iOS/Android 客户端；首期以可安装 PWA 验证移动体验。
- 训练自有基础模型。

## 3. 用户和主体

| 主体         | 目标             | 核心能力                           | 主要限制                   |
| ------------ | ---------------- | ---------------------------------- | -------------------------- |
| 工作区所有者 | 建立安全协作环境 | 工作区、成员、角色、安全和保留策略 | 高风险操作需二次确认       |
| 管理员       | 管理日常协作资源 | 项目、房间、人员、AI 和集成        | 默认不能读取密钥明文       |
| 项目负责人   | 推进一个明确成果 | 目标、成员、文档、审批和发布       | 只能操作授权项目           |
| 普通成员     | 参与讨论和撰写   | 发消息、编辑文档、调用允许的 AI    | 不能修改安全策略           |
| 审阅者       | 保证成果质量     | 评论、建议、批准文档或操作         | 不自动拥有编辑权           |
| 访客         | 参与有限协作     | 读取和评论显式共享资源             | 默认无跨项目访问           |
| AI 成员      | 在授权范围内贡献 | 回复、研究、提案、只读工具         | 无人类会话、不可自我提权   |
| 系统 Worker  | 执行耐久任务     | 重试、恢复、投影和通知             | 只能处理任务载荷指定作用域 |

## 4. 第一条完整任务

### 4.1 成功路径

1. 所有者创建工作空间和项目。
2. 项目负责人创建房间，填写目标、交付物和截止条件。
3. 负责人邀请人员并从模板或向导创建 AI 成员。
4. 成员上传或引用资料，并在消息中 @ 指定 AI。
5. API 保存消息和明确的 mention 关系，创建耐久 Agent 任务。
6. AI 只读取调用者与自身都被授权的资料，流式返回结果和来源。
7. AI 对共享文档提出结构化修改提案，正文暂不变化。
8. 人员逐项接受、修改或拒绝建议。
9. 负责人提交审阅，审阅者批准后产生正式版本。
10. 所有人能够从最终段落追溯到人员、AI、来源、运行和审批。

### 4.2 失败和恢复路径

- 消息发送失败时保留草稿和重试入口，不重复产生消息。
- Agent 断线后按事件序号恢复，不重复调用工具。
- 权限在运行中被撤销时，后续上下文读取和工具调用立即拒绝。
- AI 修改基于旧文档版本时标记冲突，不覆盖新内容。
- 预算或时限耗尽时明确停止，并保留已完成的可审阅结果。
- 审批过期或操作参数改变时，原批准自动失效。

## 5. 功能需求

### 5.1 工作空间与成员

| ID     | 需求                             | 优先级 | 验收标准                                           |
| ------ | -------------------------------- | ------ | -------------------------------------------------- |
| WS-001 | 创建、修改和归档工作空间         | Must   | 只有有权主体可操作；最后一个 Owner 不可被移除      |
| WS-002 | 邀请人员并分配成员身份           | Must   | 邀请绑定工作空间、邮箱、角色和有效期；重复接受幂等 |
| WS-003 | 在同一账户下切换工作空间         | Must   | 服务端重新解析成员身份，旧作用域令牌不可复用       |
| WS-004 | 创建自定义访问角色               | Should | 角色由稳定 capability 组成，不从页面路径推导       |
| WS-005 | 查看人员、AI、访客和停用成员目录 | Must   | 身份类型至少通过文字和图形两种方式区分             |

### 5.2 项目与房间

| ID     | 需求                       | 优先级 | 验收标准                                           |
| ------ | -------------------------- | ------ | -------------------------------------------------- |
| RM-001 | 创建带目标和成员的项目房间 | Must   | 房间属于一个工作空间和项目，私密房间仅显式成员可见 |
| RM-002 | 消息、线程、回复和提及     | Must   | 消息保存成功后不可原地覆盖；编辑产生 revision      |
| RM-003 | 明确保存人和 AI mention    | Must   | mention 是关系记录，后台任务不得重新猜测文本       |
| RM-004 | 乐观发送与失败重试         | Must   | clientMutationId 去重；失败保留原文                |
| RM-005 | 历史消息游标分页           | Must   | 首次只加载近期消息；10,000 条消息仍保持可用        |
| RM-006 | 房间状态与归档             | Should | active/waiting/completed/archived 有明确权限和审计 |
| RM-007 | 全局和房间搜索             | Later  | 权限过滤发生在排序之前，结果不泄漏标题或摘要       |

### 5.3 AI 成员

| ID     | 需求                               | 优先级 | 验收标准                                        |
| ------ | ---------------------------------- | ------ | ----------------------------------------------- |
| AI-001 | 创建具名 AI Actor                  | Must   | AI Actor 不等同于人类 User，也没有交互登录会话  |
| AI-002 | 配置职责、非职责、知识、工具和预算 | Must   | 普通设置不要求用户理解底层模型参数              |
| AI-003 | 草稿与不可变发布版本               | Must   | 每次运行固定引用 AgentVersion，历史版本不可改写 |
| AI-004 | 默认 @提及 路由                    | Must   | 无 mention 时 AI 保持沉默，不消耗模型预算       |
| AI-005 | 协调员分派模式                     | Should | 显示邀请对象、原因、汇总者和最大参与轮次        |
| AI-006 | 暂停、停用和移出房间               | Must   | 停用后不能创建新运行；进行中任务按策略取消      |
| AI-007 | 多模型供应商                       | Should | 更换 Provider 不改变 Actor、消息或权限数据模型  |

### 5.4 Agent 运行

| ID      | 需求               | 优先级 | 验收标准                                                        |
| ------- | ------------------ | ------ | --------------------------------------------------------------- |
| RUN-001 | 显式持久状态机     | Must   | 支持 queued/running/waiting_approval/completed/failed/cancelled |
| RUN-002 | 流式事件和重连恢复 | Must   | 事件有递增 seq；重复、乱序和缺口可处理                          |
| RUN-003 | 取消、重试和幂等   | Must   | 取消后无新副作用；重试生成新 run，不覆盖旧结果                  |
| RUN-004 | 多维预算           | Must   | token、费用、时长、步骤、工具和参与者均有上限                   |
| RUN-005 | 可理解的过程状态   | Must   | 展示“读取授权资料/等待批准”等摘要，不展示隐藏思维链             |
| RUN-006 | 上下文来源清单     | Should | 能查看本次使用的消息、文档、记忆与附件来源                      |

### 5.5 协作文档

| ID      | 需求                 | 优先级 | 验收标准                                               |
| ------- | -------------------- | ------ | ------------------------------------------------------ |
| DOC-001 | 富文本编辑和自动保存 | Must   | 本地输入不因网络延迟阻塞；状态明确                     |
| DOC-002 | 正式版本与比较       | Must   | 发布、AI 修改接受和手工保存可形成 checkpoint           |
| DOC-003 | AI 修改提案          | Must   | 包含 baseVersion、操作、理由、来源和委托人             |
| DOC-004 | 逐项接受和拒绝       | Must   | 未接受内容不进入正式正文；接受后可回滚                 |
| DOC-005 | 评论与建议线程       | Should | 锚点在普通编辑后尽量保持，保留 Actor 和状态            |
| DOC-006 | 多人 CRDT 编辑       | Should | 两个客户端并发编辑后确定性收敛，不使用 last-write-wins |
| DOC-007 | 来源和引用           | Must   | 引用能打开有权限的原始位置；无权限时不泄漏摘要         |

### 5.6 审批、通知和审计

| ID      | 需求             | 优先级 | 验收标准                                       |
| ------- | ---------------- | ------ | ---------------------------------------------- |
| GOV-001 | 高风险行为审批   | Must   | 绑定操作、参数摘要、Agent、委托人和过期时间    |
| GOV-002 | 审批收件箱       | Must   | 明确展示影响、差异、对外副作用和一次性批准范围 |
| GOV-003 | 成员身份隔离通知 | Must   | 通知同时匹配 user、workspace 与 membership     |
| GOV-004 | 仅追加审计事件   | Must   | 普通管理员不能修改或删除；拒绝行为同样记录     |
| GOV-005 | 用量账本         | Should | reserve/settle/release 幂等，可重建余额        |
| GOV-006 | 保留、删除和导出 | Should | 删除传播到主库、文件、索引、记忆和缓存         |

## 6. 非功能需求

### 6.1 安全

- 默认拒绝；缺少工作空间或项目上下文时失败关闭。
- 人类会话使用 HttpOnly、Secure、SameSite Cookie，刷新令牌轮换和撤销。
- Agent 权限取委托人、Agent、资源、工具、数据和审批策略的交集。
- 所有外部内容标记为不可信数据，工具调用在执行时重新授权。
- 凭据由服务端密钥代理注入，不进入浏览器、提示词、通知或普通日志。

### 6.2 性能

- 生产 p75：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.05。
- 乐观消息 100ms 内出现；SSE chunk 100ms 内完成渲染。
- 文档本地输入反馈 ≤ 50ms；同区域协作更新通常 ≤ 250ms。
- 消息列表窗口化，DOM 活跃消息节点建议不超过 150。

### 6.3 可用性与无障碍

- 目标 WCAG 2.2 AA。
- 支持键盘、触摸和屏幕阅读器完成所有主流程。
- 触摸目标至少 44×44 CSS 像素，支持 200% 缩放。
- 尊重 reduced motion，状态不能仅靠颜色或动画表达。

### 6.4 国际化

- 首发 zh-CN、en-US，消息键缺失时 CI 失败。
- UI 使用 ICU Message；API 返回稳定错误码与参数。
- 用户内容保留原文与 contentLanguage，翻译标记为派生版本。

## 7. 成功指标

| 指标             | 定义                                 | 首期观察目标             |
| ---------------- | ------------------------------------ | ------------------------ |
| 首次成果时间     | 创建房间到第一份被人员接受的文档版本 | 比现有分散流程更短       |
| AI 建议采纳率    | 被接受或编辑后接受的提案 / 全部提案  | 判断角色与上下文是否有效 |
| 人工返工率       | 发布后因事实或权限问题返工的段落比例 | 不高于人工基线           |
| 有效协作率       | 产生正式文档/决定的活跃房间占比      | 避免只聊天不交付         |
| 单次有效贡献成本 | 模型和工具成本 / 被接受贡献          | 可按团队预算管理         |
| 风险拦截质量     | 正确升级或拒绝 / 全部风险决定        | 同时观察误报和漏报       |

## 8. MVP 完成定义

只有以下端到端链路在中英文、桌面和手机上均通过，MVP 才算完成：

1. 两名人员进入同一房间并可靠收发消息。
2. 人员 @ 一个 AI，收到可停止、可重试、可恢复的流式回复。
3. AI 只能读取授权消息和文档，并显示来源。
4. AI 提出文档修改，人员查看差异并接受其中一项。
5. 接受动作产生新文档版本和完整审计链。
6. 权限撤销后，现有 WebSocket、下载链接和 Agent 后续工具调用失效。
7. 模拟断线、重复事件、Worker 崩溃和预算耗尽后，系统仍保持一致。
