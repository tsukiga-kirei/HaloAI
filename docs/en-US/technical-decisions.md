# HaloAI technical decisions

## Status and decision horizon

This document is the current architecture decision record summary for HaloAI. It defines the technology boundaries for the first usable internal alpha, called the MVP below, and records already accepted directions that activate in later delivery phases.

An accepted decision is binding when its phase begins. A deferred technology MUST NOT become a required dependency, deployment component, or hidden production assumption during the MVP. Replacing an accepted decision requires a new decision record, measured evidence, a data and protocol migration plan, and a tested rollback path.

## Definition of pure TypeScript

Pure TypeScript means:

1. HaloAI-owned application and business behavior in apps and packages is authored in TypeScript.
2. The web, API, Worker, realtime server, policy engine, Agent runtime, provider adapters, tool gateway, and collaboration orchestration require only the supported Node.js runtime.
3. CSS, SQL migrations, JSON, Markdown, shell-neutral container configuration, and generated artifacts are permitted supporting formats.
4. PostgreSQL, object storage, model providers, browsers, and MCP services are infrastructure boundaries, not additional HaloAI application languages.
5. A reviewed third-party package may contain compiled internals, but HaloAI accesses it through a typed package boundary and does not place product rules inside native extensions.
6. Specialized future computation MAY run as an isolated external service only after its own decision record. It cannot own HaloAI identity, authorization, room, document, approval, memory, or audit truth.

TypeScript static types do not validate network, model, database, or user input. Every external boundary MUST use runtime validation, bounded parsing, safe defaults, and stable error contracts.

## Data and protocol evolution rules

1. package.json and the pnpm lockfile are the dependency truth. Dependency ranges MUST NOT silently select a new major in CI or production.
2. Public REST contracts, durable event envelopes, Graphile Worker payloads, tool schemas, ModelGateway events, and document schemas carry explicit versions.
3. Additive fields are preferred. Readers ignore documented unknown optional fields but reject unknown security-critical variants.
4. Database changes use expand, backfill, verify, and contract. Destructive migration is separated from the application release that stops using old data.
5. Event and job consumers deduplicate stable IDs and tolerate at-least-once delivery.
6. Agent runs record model identifier, provider adapter version, Agent version, tool versions, policy version, and budget version.
7. Yjs/document schema migration is tested against stored fixtures and mixed client versions before rollout.
8. Security updates may shorten the normal compatibility window, but still require a documented rollback or containment plan.

## System failure boundaries

### Durable truth

PostgreSQL is authoritative for identity linkage, membership, rooms, messages, run state, approvals, budgets, audit facts, document metadata, revisions, job metadata, and outbox records. Object storage is authoritative for large immutable blobs referenced by PostgreSQL. No browser store, Next.js instance, Fastify process, Worker memory, SSE connection, WebSocket connection, cache, model provider, or MCP server is authoritative for those facts.

### Fail-closed boundaries

The following failures deny or pause work rather than degrade authorization:

- missing tenant, project, room, Actor, delegation, or policy context;
- unavailable authentication or authorization decision;
- unavailable approval record for a gated action;
- unknown Agent, tool, event, job, or document schema version;
- inability to persist a required audit fact or budget reservation;
- uncertain state of an external write.

### Degradable boundaries

The following may degrade without corrupting durable truth:

- model streaming deltas may stop while the run enters a recoverable state;
- SSE clients may reconnect and replay durable events;
- WebSocket presence may disappear while document snapshots remain readable;
- optional local and future distributed caches may miss;
- semantic retrieval, when later introduced, may be disabled while explicit document access remains available;
- an unavailable model or MCP provider may fail one Agent contribution without disabling human room and document work.

## MVP exclusion gates

The MVP satisfies these decisions only when:

1. A clean install and production start require Node.js, pnpm, PostgreSQL, and the declared object-storage or local-development adapter, but not a second application language.
2. Workspace tasks run through pnpm and Turborepo, and also succeed with Turborepo cache disabled.
3. Next.js does not execute acknowledged long-running Agent work inside a request lifecycle.
4. Fastify and Worker processes can restart without losing acknowledged commands.
5. Every tenant table that contains product data has an explicit tenant key, repository filter, and RLS isolation test where RLS applies.
6. A product transaction and its Outbox event either both commit or both roll back.
7. Human authentication passes through AuthGateway; no AI Actor can obtain a human session.
8. Application and domain packages import ModelGateway contracts rather than provider SDK types.
9. AI document changes enter the proposal path and are not applied by direct editor mutation.
10. REST, SSE, and WebSocket each have the defined responsibility, version marker, authentication handshake, and reconnect behavior.
11. Runtime and deployment manifests have no required Redis, Temporal, vector database, Kubernetes, Swift, Kotlin, or native cross-platform application dependency.
12. Adding any deferred technology requires its trigger evidence, a new decision record, ownership, security review, migration, observability, cost estimate, and rollback test.
